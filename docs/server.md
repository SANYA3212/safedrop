# SafeDrop Server — режим «через сервер»

SafeDrop умеет работать двумя способами:

- **Напрямую (P2P)** — как раньше: компьютеры находят друг друга в локальной
  сети или в Radmin VPN и соединяются напрямую.
- **Через сервер** — все соединения идут через SafeDrop Server на машине с
  белым IP. Radmin не нужен: достаточно, чтобы у всех был интернет.

Режим выбирается в приложении: панель настроек → раздел **«Сервер»**.
Режимы не смешиваются: в режиме сервера прямые соединения не используются,
контакты из LAN/Radmin показаны «не в сети» (история с ними сохраняется и
вернётся при переключении обратно).

## Как это устроено

```
 SafeDrop A ──TLS──┐                      ┌──TLS── SafeDrop B
                   │   SafeDrop Server    │
 канал A→B ────────┼──► сводит каналы ◄───┼──────── канал B
 (внутри — TLS     │   и пересылает байты │
  между A и B)     │                      │
 звонок A ──UDP────┴──► TURN (3478) ◄─────┴───UDP── звонок B
```

- Каждое приложение держит с сервером управляющее соединение (TLS 1.3) и
  предъявляет ключ своего устройства — тот же, что и в P2P. Отпечаток ключа и
  есть ID устройства на сервере.
- Чтобы отправить сообщение или файл, приложение просит сервер открыть
  **канал** к собеседнику. Сервер соединяет два TCP-соединения и просто
  пересылает байты. Внутри канала устройства сами устанавливают взаимный TLS
  и проверяют, что ключ собеседника совпадает с его ID.
- Звонки и демонстрации экрана идут через встроенный **TURN** (UDP). Медиа
  WebRTC шифруется самими приложениями (DTLS-SRTP). TURN пересылает пакеты
  только между адресами, которые выдал сам, — чужие сети и службы самого
  сервера через него недоступны.

**Что видит сервер:** кто подключён (ID, имя устройства, версия), кто с кем
соединяется и сколько данных идёт. **Чего не видит:** текст сообщений,
файлы, звук и видео. Подменить собеседника сервер тоже не может: адрес
контакта (`sd-<ID>`) — это отпечаток его ключа.

Ключ самого сервера приложение запоминает при первом подключении. Если сервер
покажет другой ключ (переустановили или кто-то подменил), приложение не
подключится и спросит — кнопка «Доверять новому ключу» в разделе «Сервер».

## Установка на сервер (Linux с systemd)

Нужен компьютер с белым IP и открытыми портами:

| Порт | Протокол | Зачем |
|---|---|---|
| 47840 | TCP | приложения (сообщения, файлы, профили) |
| 3478 | UDP | TURN — звонки и демонстрации экрана |

Других портов снаружи не нужно. TURN выделяет каждому звонку внутренний
UDP-порт (по умолчанию из 49160–49400), но пересылает между ними только внутри
самого сервера, через 127.0.0.1: приложения шлют звук и видео только на порт
3478, а пакеты извне на внутренние порты сервер отбрасывает. Открывать или
пробрасывать этот диапазон не надо.

1. Скопировать на сервер три файла: собранный `safedrop-server` (см.
   «Сборка» ниже), `server/install.sh` и `server/safedrop-server.service`:

   ```
   scp safedrop-server install.sh safedrop-server.service user@сервер:~/safedrop/
   ```

2. На сервере:

   ```
   cd ~/safedrop && sudo sh install.sh
   ```

   Скрипт ставит сервер в `/usr/local/bin`, создаёт службу `safedrop-server`
   (отдельный пользователь без прав, ключ — в `/var/lib/safedrop-server`),
   придумывает пароль и пишет его в `/etc/safedrop-server.env`, открывает
   порты в ufw/firewalld (если они есть) и в конце печатает адрес, пароль и
   начало ключа сервера.

3. В SafeDrop: «Сервер» → «Через сервер», вписать адрес и пароль, нажать
   «Подключиться». Начало ключа сервера в приложении должно совпасть с тем,
   что напечатал `install.sh`.

Полезное на сервере:

- журнал: `journalctl -u safedrop-server -f`;
- сменить пароль: поправить `/etc/safedrop-server.env`, затем
  `sudo systemctl restart safedrop-server`;
- если белый IP не на сетевой карте (облако с NAT), звонкам нужен адрес:
  `SAFEDROP_SERVER_ARGS=--public-ip 203.0.113.5` в том же файле;
- обновить: положить новый `safedrop-server` и снова `sudo sh install.sh`
  (пароль и ключ сохраняются);
- удалить: `sudo systemctl disable --now safedrop-server`, затем удалить
  `/usr/local/bin/safedrop-server`, `/etc/systemd/system/safedrop-server.service`,
  `/etc/safedrop-server.env`, `/var/lib/private/safedrop-server` и ссылку
  `/var/lib/safedrop-server`.

Без systemd сервер можно запустить и вручную:

```
./safedrop-server --password 'пароль' --data ./data
./safedrop-server --help
```

Если портов мало (например, хостинг пробрасывает в контейнер всего пару
номеров), хватит одного номера: TCP и UDP на нём не мешают друг другу. Номер
снаружи и внутри должен совпадать, а пробрасывать его нужно и для TCP, и для
UDP:

```
./safedrop-server --listen 0.0.0.0:25000 --turn-port 25000 --password-file ./password --data ./data
```

В приложении тогда вписывается адрес с портом: `203.0.113.5:25000`. Номер
порта для звонков приложение узнаёт от сервера само.

## Сборка

Сервер — отдельный Rust-пакет в папке `server/`, к приложению не привязан.

```
cd server
cargo build --release                                     # для этой же системы
cargo build --release --target x86_64-unknown-linux-musl  # один файл для любого x86_64 Linux
cargo test --release
```

Для musl в WSL/Ubuntu нужны `musl-tools` и
`rustup target add x86_64-unknown-linux-musl`. Протокол описан в
`server/src/proto.rs`; этот же файл подключает приложение
(`src-tauri/src/relay.rs`).

## Проверка без второго компьютера

Сервер можно запустить в WSL, а рядом с обычным SafeDrop — два проверочных
экземпляра приложения. Переменная `SAFEDROP_DATA_DIR` даёт экземпляру
отдельную папку данных и папку приёма файлов; ярлык «Пуск», меню Проводника
и автозапуск обычной установки он не трогает. Профиль WebView2 тоже нужен
свой:

```
set SAFEDROP_DATA_DIR=C:\temp\sd1
set WEBVIEW2_USER_DATA_FOLDER=C:\temp\sd1\wv2
safedrop.exe
```

## Ограничения

- Сообщения не хранятся на сервере: если собеседник не в сети, сообщение ждёт
  у отправителя и уйдёт, когда тот появится (как и в P2P).
- Все, кто подключён к серверу с верным паролем, видят друг друга и сами
  появляются в контактах. Сервер — для своих.
- TURN работает по UDP и IPv4. Если у кого-то UDP закрыт, звонки через сервер
  у него не соединятся (сообщения и файлы пойдут).
- Скорость файлов через сервер упирается в канал сервера.
